## 安全性 bug 修正審查（本次審查的重點）

原規則：

```js
/^node(\s|$)[\s\S]*(^|\s)(-r|--require|--import|--loader|--experimental-loader|-e|--eval|-p|--print)(=|\s|$)/
```

修正後：

```js
/^node\b[\s\S]*(?<=^|\s)(-r|--require|--import|--loader|--experimental-loader|-e|--eval|-p|--print)(=|\s|$)/
```

**獨立重新驗證**（不沿用實作時的測試案例，另外設計了 5 組對抗性案例交叉檢查）：

```
node somefile-e.js          -> false（不誤傷檔名裡含 -e 的情況）
node --check --print         -> true
node script.js --require=./x -> true
node -e=1                    -> true（等號寫法也擋得住）
nodejs -e "1"                -> false（不誤傷 nodejs 這個不同的執行檔名）
```

加上原本 T-007 報告裡的 9 組案例全數通過。**根因分析正確**：原規則用了兩個都會消耗一個空白字元的分組（`(\s|$)` 和 `(^|\s)`），當 `-e` 緊接在 `node` 後面、中間只有一個空白時，兩個分組搶同一個字元，導致最常見的 `node -e "..."` 攻擊寫法反而漏放。修法用零寬 lookbehind `(?<=^|\s)` 取代第二個消耗性空白，邏輯正確，且沒有引入新的誤傷（allowlist 允許的 `node --check ...` 系列用法確認不受影響）。

這個修正雖然超出「補測試/CI」的原始任務範圍，但屬於：(a) 寫測試的直接副產物，不是憑空塞進來的、(b) 修法只有一行 regex、(c) 屬於安全關鍵路徑（denylist 是防止代理執行任意程式碼的最後一道防線之一）。判斷值得在同一個 PR 內處理，比另開工單延後上線更合理——**這不是範圍蔓延，是負責任的處理方式**。
