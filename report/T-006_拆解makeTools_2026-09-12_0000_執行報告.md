## 需求說明與範圍調整

原規格書（[todo/spec/拆解makeTools.md](../todo/spec/拆解makeTools.md)）設想把 `makeTools()` 的 28 個工具依「檔案 / browser / git / 其他」四類全部拆成獨立檔案。實際動手盤點後發現：**這 28 個工具對共用可變狀態的耦合程度差異很大**，不能一視同仁地拆。

### 為什麼縮小範圍

`makeTools()` 內部有多組跨工具共享的可變狀態：

- `root`（會被 `enter_worktree`/`exit_worktree` 重新賦值，之後所有檔案類工具的 `pathFor` 都要看到新值）
- `開いたタブ` / `いま見ているタブ`（browser 工具群共用，且 `stopBackground` 在函式最尾端也會讀取）
- `background` / `番`（背景指令計數與追蹤，`run_command` 寫、`read_command_output` 讀、`stopBackground` 清）
- `readAt` / `failedWrite`（檔案工具的樂觀鎖狀態）

要安全拆開這些工具，必須把上述可變狀態包成一個共用的 context 物件傳給每個子模組工廠函式，而且**目前完全沒有自動化測試**（T-007 還沒執行）能在拆完後立即驗證 `run_command` 的背景程序生命週期、`enter_worktree`/`exit_worktree` 的 `root` 切換、browser 工具的分頁狀態機這些有狀態行為沒有被拆壞。在沒有測試安全網的狀況下對這批工具動刀，風險與可能造成的損害（例如背景指令殺不掉、worktree 切換後路徑守衛失效）不成比例。

**因此本次只拆出真正無狀態、彼此獨立的 8 個工具**，其餘 20 個（檔案 I/O、browser、git worktree、背景指令）留在 `tools.js` 原地，待 T-007 補上測試後再評估是否值得繼續拆。這是刻意的範圍縮小，不是規格書資訊不足導致的暫停——原規格書設想的四類分法本身沒錯，只是執行順序（先測試、後拆有狀態工具）需要調整。

## 實作內容

### 修改檔案

- `src/tools.js`：移除 `config`、`codebase_search`、`web_search`、`web_fetch`、`update_todos`、`read_rule`、`search_skills`、`read_skill` 共 8 個方法定義，改用 `...makeQueryTools({...})` 展開（2686 → 2457 行）
- 新增 `src/tools/query-tools.js`（271 行）：`makeQueryTools(deps)` factory，回傳上述 8 個工具，透過參數接收 `ToolError`、`clip`/`clipMiddle`/`withFull`/`wantName`、`CONFIG_OPEN`、`globalrules`、`webfetch`、`normalizeTodos`/`todoCount`、`spawnAgents`、`seenUrls`、`onTodos`、`readSetting`/`writeSetting`、`askOrPass`——這 8 個工具彼此獨立、不觸碰 `root`/`開いたタブ`/`background` 等共用可變狀態，用參數注入即可安全拆開，不需要共用 context 物件

### 為何用腳本而非手動編輯

用 `sed` 精確截出原始行號範圍（1147-1193 為 `config`，1361-1560 為 `codebase_search`...`read_skill`，兩段本身在原檔案中就是連續的方法定義），直接串接組成新檔案，**方法內容逐字元未動**；`tools.js` 那側用 Python 依原始行號刪除這兩段、插入 `...makeQueryTools({...})` 展開呼叫，避免手動搬移 247 行程式碼時打錯字。
